# for. Pocket · 对话需求交接索引

这份文件把本次对话中已经提出过的产品目标、修正意见和未完成事项整理成可执行索引，供下一个 agent 接续。它不复制任何 token、cookie、`.env` 内容或私人账单；源码、Git 提交与测试结果才是事实来源。

## A. 产品初心与基本约束

1. 打开应用要能立刻记账；数字大屏、云朵、细腻高帧互动是主视觉。
2. 保持简约、可爱、奶白/抹茶的生活手账感，减少文字噪音与英文小字。
3. 参考 Life360 的轻量圈子体验与 Telegram 的触控、回弹、转场手感。
4. 默认 JPY；中、英、乌三语都要是自然表达，不用简单逐字翻译。
5. 不在用户可见文案里反复强调“AI”；功能可以使用 Gemini/Vertex AI，但界面只说“分析/识别”等自然词。
6. 不要全天后台定位或耗电追踪；位置按需获取，授权后可自动复用，拒绝时静默降级。
7. 动效优先使用 transform/opacity，不能阻塞记账；同时保留可访问性和至少 44px 的触控目标。

## B. 需求演进（按对话顺序归并）

### 1. 记账首页与语言

- 最初目标是 Telegram bot 小工具：打开后出现数字大屏，快速输入金额，选择胃、学习、日常用品、兴趣、旅游等用途，并允许自定义。
- 币种明确为日元 JPY。
- 增加中文、English、Українська切换；保留可爱、简约、低噪音视觉。
- 先出现过 Xingrun / Liia 两个付款人按钮，后改为可自定义用户，删除固定角色；账单记录显示实际成员。
- 引入 TelegramUI 组件库和基础样式，动效与交互参考 Telegram。

### 2. 页面结构、账本和登录

- 保持 Life360 式圈子体系，但首页必须迅速记账，其他功能不能抢主视觉。
- 记账确认移到云朵旁的小方格；今日支出、小账本和其他信息不应挤压金额与确认键。
- 后续又要求“备注页直接提交”，本轮已完成：备注抽屉里可以直接记下这笔，不用关闭再点云朵。
- 个人页/设置页/小账本不要出现其他成员的多余头像；首页底部只保留头像，不显示用户名。
- 圈子管理员可直接点圈子名称改名；圈子菜单、设置字体字号、排版需要统一。
- 登录状态要稳定；Google/Telegram 绑定与 Cloud Run 配置保持现状。
- 项目从 C 盘迁到 `D:\Projects\Tools\for-pocket`，Render 暂停，Google Cloud Run 为正式平台。

### 3. 小云朵与动效

- 云朵要保持以前的简约可爱形象，去掉不必要高光、绿框、素材自带气泡和异常白块。
- 点击状态顺序：闭眼笑、害羞、疑惑、叹气、小生气、再到更强的生气/爆开；重复状态不能相同，第六/第七次逻辑要清楚。
- 爆开后从顶部掉落日本“止まれ”路牌；路牌按点击来回晃动，连续点击幅度逐渐合理变大，最后丝滑恢复；路牌缺帧时要有稳定的内联 fallback。
- 汗珠不能从眼睛流出；吐气应是固定、可爱的 puff；生气只挂一个小符号并轻微泛红，不能偏离可爱路线。
- 天气/时间可影响伞、墨镜、睡帽等环境状态，但不要破坏主形象；点击和未点击时都要有逻辑微动。
- 现金飞走时云朵是哭脸并带动效；存钱时云朵接住钱并塞进棉花里。
- 用户曾要求生成五个云朵候选形象和配套帧素材；现有可用素材集中在 `public/assets/mascot/` 与 `public/assets/ui-kit-v1/`，继续生成前先复用现有资产并检查透明度/加载 fallback。

### 4. 键盘、确认和页面适配

- 数字键盘要饱满，手机不能显示成扁条，垂直间距不能留下大块空白。
- 点击按键要有 Telegram 风格的触感、声音、回弹和高帧反馈；不能重复输入，拖出/多指/失焦/硬件键盘都要稳定。
- 本轮已让手机网格行由按键填满，并优化按压 transform；见 `src/ui-polish.css`。
- 确认按钮要好看、容易点，不能只靠很小的对号；备注页已加入带文字的直接提交按钮。
- 曾明确不要加号计算器，因此不要重新引入 `350 + 480` 键盘扩展，除非后续重新确认。
- 分类从 2x3 大卡片改为单行水平胶囊抽屉，按使用频次排序，旧分类要兼容。
- 小账本右滑显示删除/复制/编辑，去掉左滑；列表、快速整理和图标都必须可点击且不挤压。

### 5. 账本、同步和位置

- 个人账本只显示自己的记录；圈子账本显示该圈成员的记录。A（个人）不能出现 B/C 圈子成员；B/C 只显示各自成员。
- 同一个人自己的记录按约定同步到其可见账本；历史数据也要按新规则过滤，不能把别人的记录泄漏进个人账本。
- 点击其他头像可叠加查看对应账目；默认小账本显示自己的总数，相关筛选放入设置抽屉。
- 位置授权一次后可持续自动带入；打开页面或开始记账时自动同步实时位置，失败则不阻断。不要显示“已附上位置”这类奇怪文案；无位置就不显示标签。
- 自动位置更智能：地点/商圈/国家用于商户提示和货币建议，但不做全天追踪。
- 账单可按分类筛选，并在条目上显示低噪音地点足迹。

### 6. 文件、语音与一句话识别

- 支持 Telegram 文本、图片/截图、小票、语音/音频，以及网页多选文件：图片、Excel、Word、PDF、TXT/CSV；大文件和过长文本需友好分批或提示。
- 统一使用 Gemini 3.1 Flash-Lite 作为默认结构化解析模型，价格按用户最后确认的实际费率口径；复杂失败重试模型需以后重新确认，不能私自改变默认模型。
- 解析金额、类别、商户、备注、时间、付款人、分摊与币种；没有明确其他币种时默认 JPY。
- 中午十二点、新宿拉面这类自然语言必须正确落到时间、商户和餐饮/外食分类，不能误判为“其他”。
- 语音最多 60 秒，识别失败要短句提示“没听清具体的账目，请再说一次或直接打字哦～”。识别成功显示确认卡；自动模式与手动确认都要安全落库。
- 普通闲聊保持古灵精怪但自然、短；含记账意图必须走记账解析，不能被闲聊分支吞掉。

### 7. Telegram 通知、摘要和表情

- 消费记录发给伴侣时全部静音；记账本人不再收到自己的消费消息。
- 每日摘要要短、像正常的鬼马朋友，cue 到每个人，花了/没花、花在哪和一句小评价即可；不写长篇审计，不输出鸡汤。
- 摘要消息每天自动清理；表情计数属于阅后即焚。定时调度按用户时区的 10:00/13:00/20:00，22:00 无记录提醒也要短而可爱。
- 删除账目要同步删除 Telegram 卡片；编辑要原地替换，不连发新消息。
- Life360 风格的头像互动：点对方头像弹出可横滑的多 emoji 面板，可连续发送；接收方平滑弹出，超过 5 个变成满屏大表情并显示 `✖️N`；间隔不超过 3 秒归组，结束后延迟静默汇总。
- 发送表情和接收表情的计数、排序、重试都要避免重复；不要在非首页错误地隐藏互动入口。

### 8. 部署与交接

- 正式平台是 Google Cloud Run，不再部署 Render；保留免费方案，不主动升级持久盘。
- Cloud Scheduler/消息队列授权曾需要用户在 Google Cloud Console 点击授权；脚本默认先 dry-run，真实云操作要保留现有授权约束。
- 推送到 GitHub `main` 触发 Cloud Build。部署检查必须核对 `/health`、Google/Telegram 配置和 revision。
- 本轮用户追加的要求是：把正在做、已完成、未完成和计划书都放到 GitHub，方便下一个 agent 接棒；本交接目录就是对应落地点。
